# Porting from SQL Server — the differences that bite

## Identifiers and casing

This is the number-one source of "it worked in the other database".

| Aspect                      | SQL Server                                   | Postgres                                                    |
| --------------------------- | -------------------------------------------- | ----------------------------------------------------------- |
| Unquoted identifier         | case-**insensitive**, stored as written       | folded to **lower case**                                     |
| Quoted identifier           | `[Name]` or `"Name"`, still case-insensitive  | `"Name"` is case-**sensitive** and must match exactly         |
| `CREATE TABLE Orders`       | object is `Orders`, `orders` also resolves    | object is `orders`; `"Orders"` will not resolve               |
| EF-generated SQL            | quotes, but casing does not matter            | quotes `"Orders"."CustomerId"` — so hand-written SQL must quote identically |
| Schema separator            | `dbo.Orders`, `dbo` is the default            | `public.orders`, resolution follows `search_path`             |
| System catalog              | `sys.tables`, `sys.columns`                   | `pg_catalog.*` and `information_schema.*`                     |

Pick one convention per database and enforce it: either **all snake_case unquoted** (the Postgres
idiom, and what hand-written SQL and psql expect) or **all quoted PascalCase** (what EF produces by
default). Mixing them means every query needs to know which table it is touching.

## Types

| SQL Server               | Postgres                          | Note                                                    |
| ------------------------ | --------------------------------- | ------------------------------------------------------- |
| `nvarchar(n)` / `varchar(n)` | `text` or `varchar(n)`        | `text` has no penalty; a length is a constraint, not an optimisation |
| `nvarchar(max)`          | `text`                            | large values are transparently stored out of line        |
| `datetime2`              | `timestamp`                       | wall clock, no zone                                      |
| `datetimeoffset`         | `timestamptz`                     | stores the instant; the offset is not preserved           |
| `bit`                    | `boolean`                         | `true`/`false`, not `1`/`0`                              |
| `uniqueidentifier`       | `uuid`                            | native                                                    |
| `varbinary(max)`         | `bytea`                           |                                                          |
| `money`                  | `numeric(19,4)`                   | avoid the `money` type in both                            |
| `int IDENTITY`           | `integer GENERATED BY DEFAULT AS IDENTITY` | or the legacy serial pseudo-type              |
| `tinyint`                | `smallint`                        | there is no 1-byte integer                                |
| `rowversion`             | the system column `xmin`          | used as an EF concurrency token                            |
| table type / TVP         | array type, or `unnest(...)`      | arrays are first class here                               |
| `xml`                    | `xml`                             | supported, but JSONB is the idiomatic document type        |

`timestamptz` is the default choice for anything that is a point in time. Store UTC, and let the
client enforce the `DateTime.Kind` — see `npgsql-dotnet.md`.

## Strings, comparison and collation

| Behaviour                       | SQL Server                                | Postgres                                            |
| ------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| Default comparison              | case-**insensitive** collation, usually    | case-**sensitive**                                   |
| Case-insensitive equality       | free                                      | `lower(col) = lower($1)` + expression index, `citext`, or a non-deterministic ICU collation |
| Trailing spaces in comparison   | `varchar` pads and ignores them            | significant — `'a' <> 'a '`                          |
| `LIKE` case-insensitivity       | follows the collation                      | `ILIKE`, or `lower()` on both sides                  |
| Concatenation                   | `+` (and `+` with NULL yields NULL)        | `\|\|` — `+` on strings is an error                  |
| `''` versus `NULL`              | distinct                                   | distinct (same as SQL Server)                        |
| Sort order for pagination       | collation-dependent                        | collation-dependent, and **different** — a keyset paginator ported verbatim can skip or repeat rows |

Changing a collation later rewrites indexes, so decide the case-sensitivity story when the table is
created, not when a bug appears.

## Syntax translation

| SQL Server                            | Postgres                                                       |
| ------------------------------------- | -------------------------------------------------------------- |
| `SELECT TOP 10 ...`                   | `SELECT ... LIMIT 10`                                           |
| `OFFSET n ROWS FETCH NEXT m ROWS ONLY` | `LIMIT m OFFSET n` (the standard form also works)              |
| `ISNULL(a, b)`                        | `COALESCE(a, b)`                                                |
| `GETDATE()` / `SYSUTCDATETIME()`      | `now()` / `now() AT TIME ZONE 'utc'`                            |
| `LEN(s)` / `DATALENGTH(s)`            | `length(s)` / `octet_length(s)`                                 |
| `CHARINDEX(a, b)`                     | `position(a in b)` / `strpos(b, a)`                             |
| `SUBSTRING(s, 1, 3)`                  | `substring(s from 1 for 3)`                                     |
| `CAST(x AS int)`                      | `cast(x as integer)` or `x::integer`                            |
| `CROSS APPLY` / `OUTER APPLY`         | `CROSS JOIN LATERAL` / `LEFT JOIN LATERAL ... ON true`          |
| `SCOPE_IDENTITY()`                    | `INSERT ... RETURNING id`                                       |
| `IDENT_CURRENT` / `@@IDENTITY`        | `currval('seq')` / `nextval('seq')`                             |
| `MERGE`                               | `INSERT ... ON CONFLICT (key) DO UPDATE SET ...` — see below     |
| `#temp` / `##global`                  | `CREATE TEMP TABLE t AS ...` (session-scoped, no global form)     |
| `SELECT ... INTO #t`                  | `CREATE TEMP TABLE t AS SELECT ...`                              |
| `WITH (NOLOCK)`                       | nothing — readers never block under MVCC                         |
| `WITH (UPDLOCK)`                      | `SELECT ... FOR UPDATE`                                          |
| `sp_executesql` with parameters       | `EXECUTE format('...%I...', ident) USING value` inside PL/pgSQL   |
| `STRING_AGG(x, ',')`                  | `string_agg(x, ',')`                                             |
| `IIF(c, a, b)`                        | `CASE WHEN c THEN a ELSE b END`                                  |
| `TRY_CONVERT`                         | no direct equivalent — a function with an exception block          |
| Stored procedure returning a result set | a function returning `TABLE(...)`/`SETOF`, or a cursor          |

## Upsert

```sql
INSERT INTO cache_entry (key, payload, updated_at)
VALUES ($1, $2, now())
ON CONFLICT (key) DO UPDATE
   SET payload = excluded.payload, updated_at = excluded.updated_at
 WHERE cache_entry.payload IS DISTINCT FROM excluded.payload;   -- skip a no-op write
```

`ON CONFLICT` requires a unique index or constraint on the conflict target — there is no "upsert on
an arbitrary predicate". `excluded` is the row that was proposed. The optional `WHERE` avoids writing
a new row version (and therefore a dead tuple) when nothing changed; on a hot cache table that alone
can remove most of the vacuum load. `DO NOTHING` is the idempotent-insert form.

## Sequences

Sequences are independent objects, not a table property. Consequences when porting:

- A restored dump can leave a sequence behind its table's maximum id → `setval` it after a data load
  that inserted explicit ids.
- `nextval` is **not** rolled back by a failed transaction, so gaps are normal and expected.
- `GENERATED ALWAYS AS IDENTITY` rejects an explicit value (use `OVERRIDING SYSTEM VALUE` to force
  one); `GENERATED BY DEFAULT` allows it, which is what a data migration needs.

## Transactions and DDL

**DDL is transactional here.** `CREATE TABLE`, `ALTER TABLE`, `DROP`, even `TRUNCATE`, can be rolled
back inside a transaction — a genuine advantage for migrations, where a half-applied schema change is
the usual disaster on SQL Server. The exceptions are the concurrent index operations
(`CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`), which cannot run inside a transaction and
therefore need their own migration step.

Other behavioural differences worth knowing:

- An error **aborts the whole transaction**: every subsequent statement fails with "current
  transaction is aborted" until a rollback. There is no equivalent of continuing after a trapped
  statement error without a savepoint.
- `SAVEPOINT` / `ROLLBACK TO SAVEPOINT` is the tool for partial rollback.
- Default isolation is read committed with MVCC snapshots, so a read never blocks and never sees
  dirty data; `REPEATABLE READ` here behaves like SQL Server's `SNAPSHOT`, including serialisation
  failures the caller must retry.
- `SERIALIZABLE` uses predicate locking and raises a serialisation error instead of blocking, so
  **every** write path needs a retry policy for error class 40001.
