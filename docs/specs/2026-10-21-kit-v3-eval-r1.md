process for 5 checks: ≈19 min over 6,762 calls/month — acceptable); `secret-scan` + `format-on-edit` ≈ 2 × 150 ms

## 5. DB policy

| Option | Pros | Cons |
| --- | --- | --- |
| **A** prod gate + local free (spec) — *as shipped it is A minus*: redis dev allow-list, host-less deny | one deny with a cheap safe route; local work unobstructed | batch 6 regressed it (K3, K4); `db-ro.ps1` exit 3 makes a prod target the owner cannot re-credential **unreadable** — the probe is a hard wall on someone else's DB |
| **B** confirm every write everywhere | simplest mental model; no host registry | the owner's fear is right: every local `UPDATE`, `SET`, `DEL`, migration apply becomes a prompt → click-through training; `sql-target` + `destructive` already know the shape, B adds nothing on prod |
| **C** hybrid | prod: raw client → deny (keep); `db-ro.ps1` probe finds write grants → **ask once** listing the grants, then run with the statement filter (SELECT/WITH only, no `;`) as the only remaining layer, said in the output · dev or host-less: allow; `destructive.js` asks on `DROP/TRUNCATE/FLUSH*/down -v` as today · redis: no allow-list on dev | prod becomes reachable without owning the users, with the owner informed each time | the statement filter is weaker than a server grant — which is exactly today's reality, now stated instead of refused |

**Recommend C.** Concretely: (1) `sql-target.js`: no host → treat as the client's local default (not deny); dev host
redis → return null; keep `--eval`/`--pipe`/stdin opacity only for non-dev. (2) `db-ro.ps1`: probe failure → exit 3
stays the default, `-AcceptWriteGrant` (or the `/db --accept-grants` token) downgrades to the filter; `db-analyst`
reports the grant list and asks the caller once per target per session. (3) `destructive.js` adds `TRUNCATE` inside
`psql -c` (design said so; not seen in RULES beyond the generic truncate regex — verify with a test). Server-side RO
users remain the TODO the owner creates when he can; the kit must not depend on it.

## 6. Communication

Measured problems: decision in line 1 on 60/400 long finals; 240 "procedo?" (74 yes); 33 % multi-ask turns answered
partially. Style rules 1, 4, 7 target exactly those three. Two defects: (a) the style is **not selected** (§4) — on a
fresh install nothing changes; (b) duplication: `CLAUDE.md` § "Write for me" (600 B) and the style (2,133 B) say the
same thing; keep one. The style is the right home (per-user, "these rules win", survives `/compact` unlike a rule).
Bloat check: 2,133 B ≈ 530 tokens/turn, cheaper than one "procedo?" round trip (a full cache read + the owner's
turn); earns its place **if** the owner wants it active. Missing: the audit script that produced the numbers is not in
`tools/`, so round 2 cannot measure first-line length, decision-in-line-1 % or "procedo?" count — add it (I9). Rule 6
("no narration between tools") stays: the audit measured 933 narrating turns at a median 451 chars — it is the only
rule aimed at that number. Rule 7's `AskUserQuestion` guidance is the one thing CLAUDE.md lacks — correct to keep it
only in the style.

## Verdict

v3 is structurally right: cost moved from prose to hooks and forks, baseline −58 %. What is broken is the last
mile — the style not selected, the nudge calibrated for a window nobody fills, the DB gate denying local dev, every
guard hanging on one env var. I1–I4 are small and mechanical; I5 is the one real design kill and needs the owner.
Round 2 is warranted **after** I1–I4 and I7 land and only if the owner decides K2: otherwise a re-evaluation would
re-read the same files to confirm the same conclusions.
